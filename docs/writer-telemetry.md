# Local writer measurements

`writer-telemetry.jsonl` keeps the existing 10 MiB limit and three backups. Beside it, `writer-telemetry-summary-YYYY-MM-DD.json` retains the current UTC date plus seven complete dates, independently of raw rotation. Each date has at most 64 producer/lane/outcome groups (excess groups go to `overflow`), with counts and metric count/sum/max/histograms. Histogram key `b` means an upper bound of `2**b` milliseconds (rows for `rows_committed`); key 0 includes zero and key 31 includes overflow. Quantiles reconstructed from these histograms are estimates, not exact samples. Missing metrics are unmeasured, never zero.

`lock_wait_ms` observes explicit IMMEDIATE/EXCLUSIVE BEGIN attempts. `lock_held_ms` sums observed successful BEGIN completion through COMMIT/ROLLBACK completion using monotonic time. Failed BEGINs never claim a held lock; implicit/deferred transactions and spans lacking a completed boundary retain null held time. Span duration still includes observer work and must not be substituted for lock-held time. No SQL queries were added to obtain these boundaries.

BrainBar writes `logs/deferred-stores.jsonl` beside its resolved database (`BRAINLAYER_DEFERRED_TELEMETRY_PATH` overrides it): `queued`, `committed`, and `replay_failed` events join on queue_id/chunk_id. New queue items preserve a subsecond origin and reason through scrub/rewrite/restart; legacy timestamps have second resolution. `queue_to_commit_ms` is wall-clock elapsed time through successful replay, not embedding or search retrieval latency. Negative clock adjustments remain visible in raw events and are excluded from latency aggregates. Daily files retain eight UTC dates with counts and latency histograms; raw lifecycle files rotate at 1 MiB with three backups.

Both sinks are best-effort and obey `BRAINLAYER_WRITER_TELEMETRY=0`. Lifecycle I/O runs on a background queue capped at 128 pending events; saturation or sink failure logs a fixed warning without changing store receipts. This is measurement, not a crash-proof receipt ledger: process death or sink failure can lose telemetry. Python sink lock contention drops events without a drop counter, so daily summary counts are lower bounds. Lifecycle records and daily summaries contain no content, tags, project names, source paths, or SQL. Retention starts at installation; missing historical dates cannot be recovered from this change.

Surface checks: entry points — all BrainDatabase queue/replay calls and MCP backup/not-open routes; clients — Python writer spans and both Swift targets share the instrumentation; providers — local SQLite only; contracts — additive fields and optional queue origin preserve legacy decoding and receipt schemas; reverse states — failed BEGIN, replay failure, disabled/unwritable sinks; connection modes — real two-connection lock and fresh/restarted router fixtures; docs — this measurement contract supplements the existing raw-tail CLI (which still summarizes only its selected raw lines).

Ingest records add `ingest_finished` stage totals and `ingest_committed` completion boundaries. Daily summary keys append the event kind so transaction counts, completed attempts, and committed cohorts remain distinct. Watermarks retain cohort minima and latest observed commit, **not** a contiguous all-sources completion frontier. Missing legacy origins remain unmeasured. Event preparation remains inside the original apply stage; no bounded-drain changes are included. Disabled drain encoding is explicitly zero; BEGIN wait, apply, COMMIT and checkpoint are separate stages, and observer/setup gaps are not assigned to another stage.

The watcher stamps complete parsed lines with `_ingest_observed_at`; new watcher rows carry this observation and their immutable enqueue epoch in metadata. Drain records DB/FTS completion before checkpointing. Hotlane extends its existing indexed eligibility lookup to read those origins and records vector completion only after a successful, nonempty vector commit. A cycle's encoder/write totals do not imply every candidate committed. No content, chunk IDs, or source names enter ingest telemetry. These boundaries measure **first observed line → DB/FTS/vector completion**, not physical source append time or the first successful real-client retrieval. Replay/dedup can resolve an already searchable row; old rows without origins cannot provide this lag.
